# AI クレジットシステム 設計

ユーザに毎月クレジットを付与し、AI 機能（地域への質問チャット、エチケット画像からの項目抽出など）を
使うとクレジットを消費する仕組みの設計をまとめる。無料会員よりプレミアム会員の方が毎月の付与
クレジット数が多い。コード配置・レイヤ構成を含む全体像は [docs/architecture.md](./architecture.md) を参照。

## 設計判断

| 項目 | 決定 | 補足 |
|---|---|---|
| 提供面 | Web UI ＋ MCP の両方 | **共通の残高プール**を両面で共有する |
| 推論の担い手 | Cloudflare Workers AI（サーバー側推論） | MCP 経由でもクライアントのモデルには委ねず、自前で推論・課金する |
| 消費粒度 | **コスト従量（実原価）** | モデル/プロバイダの単価表から µUSD を算出して計上する（後述） |
| 表示単位 | 抽象クレジット（丸めた数字） | 1 クレジット = $0.001（`MICRO_USD_PER_CREDIT`）。換算は切り上げ＝過小請求防止 |
| 残高不足時 | その月はブロック＋アップグレード誘導 | 追加購入・翌月繰越は行わない。throw ではなく `{ blocked: true }` を返す |
| 付与タイミング | 暦月一律（JST）の遅延付与 | Cron は使わない（後述） |
| 付与数 | 無料 < プレミアム | 定数は `src/lib/billing/plans.ts` が正（後述） |

> **なぜ「両面共有 × Workers AI」か**: MCP 経由でもサーバー側（Workers AI）で推論するため、
> Web UI・MCP のどちらから使っても同じ推論経路・同じ残高を通る。「MCP はクライアント（Claude 等）の
> モデルに委ねる」構成ではないので、MCP 利用時も実コストが自社に発生し、クレジット消費の対象になる。

## データモデル

**台帳方式（append-only ledger）＋ 残高キャッシュ**を採用する。付与・消費・返却をすべて追記する
ことで、履歴表示・監査・二重消費防止を一枚岩で解く。テーブル定義の正は `src/db/schema.ts`
（`credit_ledger` / `credit_balance`）、D1 アクセスは `src/lib/services/credit-service.ts`。

- **`credit_ledger`（追記専用台帳）** — `amount` は符号付きの表示クレジット（付与＋ / 消費− / 返却＋）。
  **`amount` そのものが実原価に比例する**ので、台帳から原価を復元できる。`tokenAmount` は
  見積/実測のトークン数だが、これは観測用の参考値で課金の根拠ではない（同じトークン数でも
  経路によって原価が 1000 倍違う）。`type` は `grant` / `consume` / `refund` /
  `admin_grant`（管理者の理由付き手動付与）。`requestId` は unique の冪等キーで、月次付与は
  `grant:{userId}:{YYYY-MM}`、消費は用途プレフィックス付き UUID（例 `ask_region:{uuid}`）、
  確定/返却は予約 ID に `:settle` / `:refund` を付けて導出する（接尾辞の定義は
  `src/lib/credit/reservation.ts` が SSOT）。**確定は差分が 0 でも `:settle` 行を `amount=0` で
  必ず残す**。この行が「この予約は決着済み」の唯一の証跡で、二重返却ガード（#144）と
  孤児予約の検出（後述）の両方がこれに依る。
- **`credit_balance`（残高キャッシュ）** — `userId` を PK に現在残高を保持する（台帳の SUM を毎回
  引かないため）。台帳への追記と**同一の `db.batch`** で更新し、常に整合させる。`periodMonth`
  （JST の `"YYYY-MM"`）が残高の属する付与月で、月が変わると付与時にリセットされる。

## 消費フロー（予約 → 確定）

トークン従量では消費量が事前に確定しないため、**予約（reserve）→ 実測確定（settle）**方式を採る。
実装は `credit-service.ts` の `reserveCredits` / `settleReservation` / `refundReservation` で、
消費者は `src/lib/services/ai-service.ts`（地域 Q&A・エチケット解析・ワインリスト一括抽出）。

**この4ステップを直接書くのは `runMeteredInference`（`src/lib/services/metered-inference.ts`）
だけ**で、AI 機能側はそれを呼ぶ（#392）。以前は3つの機能が約70行の骨格を逐語コピーで
持っており、下記の順序制約（返却を担う `try` の内側／外側の別）が typecheck もテストも
強制しない「書く順番」だけで守られていた。ラッパーの不変条件は
`metered-inference.workers.test.ts` が実 D1 で固定している。

1. **最低残高チェック** — 残高が最大見積を下回るならブロック。推論は開始せず、アップグレード誘導を返す。
2. **予約** — 最大見積分を `consume` として仮計上し、残高から引く（`request_id` 付き）。
3. **推論実行** — Workers AI を呼ぶ（エチケット解析は `OPENAI_API_KEY`（GPT-5.6 Luna）/
   `ANTHROPIC_API_KEY`（Claude）設定時のみ LLM + web検索を優先し、失敗時は Workers AI へ
   フォールバック）。
4. **確定・差分返却** — 実測 usage を**実際に推論したモデルの単価**で µUSD に換算し、予約との
   差分を `refund` で戻す。推論失敗時は予約全額を `refund` で戻す。

   > **意図した経路ではなく実行した経路の単価で課金する**。高精度経路が失敗して Workers AI へ
   > 降格した回に Opus の単価で Llama の推論を課金しないため。換算は `ai-service.chargeFor`
   > の1箇所に寄せてある（経路ごとに書くと必ずドリフトする）。

```
[残高チェック] → NG → ブロック（アップグレード誘導）
      │ OK
[予約: consume -max]
      │
[Workers AI 実行] → 失敗 → [refund +max]（全額返却）
      │ 成功
[settle: refund +(max - 実測)]（差分返却）
```

> **なぜ予約するのか**: 残高不足ブロックを「推論後」に判定すると、コストだけ発生して課金できない
> ケースが生まれる。先に最大見積を押さえることで、必ず残高の範囲内で推論する。

- **見積は「最悪値」ではなく実測の中心値に置く**。コスト基準では最悪値（出力上限まで生成 +
  web検索を上限まで実行）の予約額が月次付与を超え、その経路が誰にも一度も使えなくなるため。
  上振れしたぶんは取りこぼす（settle は予約を超えて課金しない＝過小請求側に倒れる）。
- 実測 usage が取得できないモデルでは予約全量を実測とみなす（返却 0 の安全側）。
- 1 回の予約は `AI_MAX_ESTIMATE_MICRO_USD` でキャップする（暴走・過大請求のガード）。
- **解析前に必要クレジットを UI に出す**。経路によって消費が2桁変わるので、押してから
  残高不足で弾かれると理由が分からない。表示はサーバの予約と同じ
  `estimate*ReserveCharge`（`src/lib/ai/config.ts`）を通す。

## 打ち切りへの備え（孤児予約の回収）

上のフローは「失敗が JS 例外として catch に届く」ことを前提にしている。Workers はクライアント
切断・isolate 強制終了・デプロイ入替で実行を打ち切りうるため、それだけでは予約が宙に浮く（#246）。
二段構えで塞ぐ。

1. **後始末を打ち切りから守る** — 確定・返却の D1 書き込みは `credit-service.keepAlive`（`waitUntil`）
   に載せる。クライアントが切断してリクエストコンテキストが畳まれても書き込みは完走する。
   呼び出し側は従来どおり await するので、通常経路の挙動は変わらない。
2. **取りこぼしを次回に回収する** — AI 実行そのものが打ち切られると catch にも到達しないため、
   `reclaimOrphanReservations` が「猶予（10 分）を過ぎても `:settle` も `:refund` も付いていない
   consume」を洗い出して返却する。`reserveCredits` の冒頭（残高チェックより前）で呼ぶので、
   孤児のせいで残高不足になっていたユーザがそのままブロックされ続けることもない。

> **なぜ Cron ではないのか**: 月次付与を `ensureCurrentMonthGranted` の遅延実行で賄っている設計に
> 合わせ、入口でのついで回収にする。当該ユーザの行だけを見るので `credit_ledger_user_created_idx`
> が効き、対象が無い通常時のコストは 1 クエリで済む。

回収の健全性は「確定した予約には必ず `:settle` 行がある」ことに依る。差分 0 の確定が台帳に何も
書かなかった頃の既存行は、正常に消費し切った予約と孤児の区別が付かないため、
`drizzle/0020_credit_settle_marker_backfill.sql` が適用時点の未決 consume をすべて「確定済み」として
マーカーで塗り潰している（孤児を取りこぼす方向＝ユーザ不利にならない側へ倒す）。

回収と、生き延びていたリクエストの確定が競合した場合は、**先に記録された方が勝つ**:
`refundReservation` は `:settle` があれば返却せず、`settleReservation` は `:refund` があれば確定しない。
どちらも残高を二重に動かさない。

この相互排他は**書き込みバッチの中で**強制する（#335）。入口の事前 SELECT だけでは、確認からコミットまでの
間に相手側がコミットする窓が残り、全額返却と差分返却が両方効いて消費がネットマイナス（＝残高の二重加算）に
なりうるため。残高 UPDATE の条件と、マーカーを書く `INSERT ... SELECT` の双方に**相手側キーの不存在**を置き、
負けた側は残高も台帳も一切書かない（事前 SELECT は早期リターンで無駄な書き込みを避けるための最適化として残す）。

## 整合性・同時実行

Web UI と MCP の両面から同一残高を同時に叩けるため、二重消費・残高マイナスを防ぐ設計が要になる。

- **冪等キー** — `credit_ledger.request_id` の unique 制約で再送・二重計上を弾く。
- **残高の負値禁止** — 消費は `WHERE balance >= 必要量` を条件とした**条件付き UPDATE** でのみ減算し、
  空結果＝残高不足としてブロックする（Durable Object による直列化は採用していない）。
- **原子性** — D1 にトランザクションはないため、台帳追記と残高更新は同一 `db.batch` で行う。

## 月次付与（遅延付与）

Cron は使わず、**残高参照・消費の入口で必ず `ensureCurrentMonthGranted` を呼ぶ遅延付与**方式。
新しい月（JST 暦月）の最初のアクセス時に、台帳へ `grant` を追記し残高を付与額へリセットする
（繰越なし＝前月残は失効）。

- `requestId = grant:{userId}:{YYYY-MM}` と、`periodMonth <> 当月` を条件とする更新で
  二重付与・同月への二重リセット（＝消費の巻き戻し）を防ぐ。
- 当月付与済みでも、現プランの付与目標が当月の累計付与額を上回る場合は差分を追加付与する
  （`grant_upgrade`）。月途中のプレミアム昇格だけでなく、**付与額そのものの引き上げデプロイ**も
  この経路を通る。冪等キーは `grant_upgrade:{userId}:{YYYY-MM}:{付与目標額}` で、
  **目標額をキーに含めるのが必須**（#387）。`{userId}:{YYYY-MM}` 固定だと同一月に差分付与が
  1回しか成立せず、増額で枠を使い切った後の昇格が `NOT EXISTS(request_id)` ガードと unique
  制約に弾かれて無言で消える（課金したのに付与ゼロ・リトライでも回復しない）。
- キーの導出は `src/lib/credit/grants.ts` が SSOT。単体版（`ensureCurrentMonthGranted`）と
  一括版（`ensureCurrentMonthGrantedMany`）が同じ規約を共有する必要があるため、
  文字列連結を呼び出し側に散らさない。
- **閲覧が付与を起こしてはいけない文脈**（管理画面の残高表示など）では credit-service を経由せず
  `credit_balance` を生 SELECT する（`admin-service.ts` の方針）。
- 管理者の手動付与（`admin_grant`）は当月残高への加算であり、翌月の月次リセットで失効する
  （繰越なしの仕様に合わせた挙動）。

## UX

- **残高表示** — ヘッダに現在クレジットを表示。取得中は確定表示を出さない（フラッシュ回避。
  `shouldShowAds` と同じ考え方）。
- **残高不足導線** — ブロック時はプレミアムのメリット（付与数の多さ）を示すアップグレード誘導。
- **MCP 側のブロック表現** — クレジット不足を構造化エラー（`isError: true` ＋残高・必要量の説明）で
  返し、クライアントに「アップグレードで解決する」ことを伝える。

## 単価表（コスト基準の計上）

**モデル/プロバイダごとの単価は `src/lib/billing/ai-pricing.ts` が SSOT**。ここ以外に単価を
書かない。

### なぜコスト基準なのか（Issue #355）

転換前はトークン数だけで計上していた（`TOKENS_PER_CREDIT = 1000` の一律換算）。高精度経路が
増えた結果:

- 「Opus の 1 トークン」と「Gemma の 1 トークン」が同じ 1 トークンとして課金され、経路ごとの
  実費差 **1000 倍** がクレジットに反映されなかった。
- web検索は **$10/1000 回の回数課金**でトークン基準では原理的に表現できず、
  `usage.server_tool_use.web_search_requests` をどこも読んでいなかったため**まったく計上されて
  いなかった**（既定の Luna 経路は原価の 8 割がこれ）。

### 単位と恒等式

内部単位は **µUSD（マイクロUSD、整数）**。単価を「USD per MTok」の数値でそのまま持つと

```
µUSD = トークン数 × (USD per MTok)
```

という除算なしの恒等式が成り立つ（30,000 tok × 5 = 150,000 µUSD = $0.15）。公式の価格表記を
そのまま書き写せる形にしてあるので、価格改定時は数値だけ差し替える。

使用量は `AiUsage`（入力/出力/キャッシュ読み書き/web検索回数）で表し、**見積と実測が同じ型・
同じ換算関数（`usageToMicroUsd`）を通る**。見積だけ古いまま残ることがない。

### 単価表の運用

- **モデルを足したら単価も足す**。`ai-pricing.test.ts` が「実際に呼ぶモデルID
  （`AI_LABEL_ROUTE_MODELS` / `AI_REGION_QA_MODELS` / `AI_WINE_LIST_ROUTE_MODELS`）がすべて単価表にある」
  ことを検証するので、忘れると CI で落ちる。
- **単価未登録は throw しない**。settle は推論成功の**後**に走るため、ここで throw すると成功した
  推論が失敗扱いで全額返却され、原価だけ出てクレジットを取り損ねる。表中の最高単価へフォール
  バックし、警告ログを出す。
- **価格改定を跨いで原価を割らない側に倒す**。例: Claude Sonnet 5 は 2026-08-31 まで導入価格
  $2/$10 だが、単価表には 2026-09-01 以降の標準価格 $3/$15 を入れてある。導入価格を書くと 9 月に
  入った瞬間から黙って過小請求になる。
- 価格の一次情報は各エントリの `@see` にあるURL。確認日も併記する。

### 数値

付与数は `src/lib/billing/plans.ts` の定数が正。**原価予算から逆算した値**で、勘で置いた数字では
ない（1 クレジット = $0.001 なので、付与数はそのまま「その会員に毎月許容する AI 原価の上限」）:

| | 付与 | 許容原価/月 |
|---|---|---|
| 無料 | `MONTHLY_CREDITS_FREE` = 200 | $0.20 |
| プレミアム | `MONTHLY_CREDITS_PREMIUM` = 1500 | $1.50 |

無料枠は #474 で 150 → 200 に引き上げた。一括抽出が web 検索で裏を取るようになり、Claude 経路
（Sonnet 5）の写真 1 枚が 126 → 156 クレジットになって 150 に収まらなくなったため。「写真 1 枚の
解析は無料会員の付与内に収まる」を不変条件として維持する側を選んでいる。

プレミアムは ¥300/月（Stripe 手数料後で約 $1.87）なので、付与枠を最も高価な経路で使い切られても
収益内に収まる。1 回の予約上限（`AI_MAX_ESTIMATE_MICRO_USD` = $0.40）はプレミアム付与の 3 割弱で、
1 回の推論が付与枠を一気に食い潰さない。

**この単位の変更に伴うデータ移行は不要**。繰越なし・月次リセットの設計なので、翌月の
`ensureCurrentMonthGranted` で全員が新しい付与額へリセットされる。台帳の過去行は当時の基準の
まま残る（追記専用の監査記録として正しい）。

### 経路ごとの消費（2026-08 時点の中心値見積、写真1枚）

| 経路 | モデル | 消費 |
|---|---|---|
| 地域Q&A | `@cf/google/gemma-4-26b-a4b-it` | 1 |
| エチケット解析 標準 | `@cf/meta/llama-4-scout-17b-16e-instruct` | 約 4 |
| エチケット解析 高精度 | `gpt-5.6-luna` + web検索 | 約 39 |
| エチケット解析 高精度 | `claude-opus-5` + web検索 | 約 275 |
| ワインリスト一括抽出 | `gpt-5.6-luna` | 約 11 |
| ワインリスト一括抽出 | `claude-sonnet-5` | 約 126 |

無料枠（150）で何ができるかは経路で大きく変わる:

- 地域Q&A・エチケット解析の標準経路は月に数十回使える。
- 高精度経路は Luna が月 3 回程度。**`claude-opus-5`（275）は 1 回も使えず、実質プレミアム専用**。
- 一括抽出は Luna なら上限の 10 枚（22）でも枠に収まる。Claude 経路は写真 2 枚まで（3 枚で 162 > 150）。

一括抽出の経路はエチケット解析と同じユーザ設定（`preferredLabelEngine`）で決まり、**既定は
`gpt-luna`**（#426）。**この経路だけは Workers AI へ降格しない**（#358: Llama 4 Scout は配列の
構造化出力が安定せず、リスト写真の読み取り品質も低い）ため、「標準（Workers AI）」を選んでいる
ユーザも高精度経路に載る。どちらのプロバイダキーも無い環境では機能ごと隠す。

Claude 経路が `claude-opus-5` ではなく `claude-sonnet-5` なのは無料枠の制約から来ている。opus だと
写真 1 枚（約 200）で無料枠を超え、無料会員がこの機能を一度も使えなくなる
（`wine-list-extraction.test.ts` の「どの経路でも写真1枚の解析は無料会員の月次付与内に収まる」が
この境界を固定している）。
